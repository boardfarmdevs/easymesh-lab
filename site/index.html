boardfarmdevs labs · Physical EasyMesh

The EasyMesh protocol on a real extender, one message at a time

A controller written from scratch in Python speaks IEEE 1905.1 and EasyMesh over raw Ethernet to a certified extender, the TP-Link RE653BE. A browser panel shows every CMDU and TLV, correlates requests with responses, draws the topology and sends commands. Phones, tablets and laptops join the extender's 2.4, 5 and 6 GHz networks, and USB Wi-Fi 7 adapters add managed clients for repeatable tests.

Run it Source on GitHub

What it is

The fifth project of the boardfarmdevs EasyMesh labs, and the only one on physical hardware. The other four simulate radios on wmediumd; this one checks the protocol against a certified device, real radios and real clients. Its name is one letter from the umbrella's: easymesh-lab is this lab, easymesh-labs the umbrella.

Controller

1905.1 and EasyMesh from scratch

Python on a raw Ethernet socket: topology discovery and queries, AP capabilities, WSC M1/M2 credential exchange with its crypto, SSID changes and re-onboarding, metrics, beacon queries, channel selection, policy, steering and raw TLVs. Unknown TLVs stay visible as bytes.

Teaching panel

Every message, decoded and correlated

Vanilla JavaScript in the browser: the packet timeline with TLV trees and raw hex, an oscilloscope view of the exchange, a command studio that previews before it sends, radios and telemetry, a spring-layout topology, speed tests and guided experiments.

Physical setup

A certified extender and real clients

A TP-Link RE653BE on a dedicated USB Ethernet adapter. Phones, tablets and laptops join its tri-band BSSes; enrolled MT7925U USB Wi-Fi 7 adapters act as managed stations, each in its own network namespace, for iperf3 through the extender.

The teaching panel

Each view is a learning task. A queued command is not success: the panel keeps sent, acknowledged, response received, no response and an operational-SSID confirmation apart, and a steering request counts as done only when a later association report shows the client on the target.

What the extender showed

Observations from one device and firmware, not claims about every EasyMesh agent. Device identities, credentials and raw captures stay out of the public repository.

ExperimentObserved
2.4 and 5 GHz onboardingThe agent's M1, the controller's encrypted M2, then the expected SSID in the operational BSS reports
SSID changeA renew, a fresh M1/M2, and the new SSID confirmed by topology

6 GHz clientsWith onboarding responses paused, a manually enabled 6 GHz BSS held; a Mac laptop joined it, and the managed USB clients join it with WPA3-SAE and PMF
Client signalAssociated STA Link Metrics give the AP's receive power (RCPI) for each client; no noise, so no SNR
Periodic discoveryThe Ethernet link and associations dropped after a discovery exchange; the running lab suppresses periodic announcements for the known agent (a diagnostic setting, not a fix)
Guest against hostThe same USB Wi-Fi client on 6 GHz / 160 MHz measured about 74/65 Mbps inside the VM against 739/446 Mbps on the host: USB passthrough is the open question

Current state

  • Where: a fresh LXD VM, easymesh-lab, on rev120, the host the extender's USB Ethernet adapter and the USB Wi-Fi clients are attached to. Physical tests run there.
  • Checked: 34 tests, plus the browser, reboot, capture and 6 GHz / WPA3 checks; the previous VM was backed up and removed.
  • Works: discovery, topology, AP capabilities, 2.4/5 GHz WPA2 provisioning and re-onboarding, metrics, the packet timeline and oscilloscope, topology, client history and signal, speed tests, managed WPA3 clients on 6 GHz.
  • Not yet: controller-provisioned 6 GHz; more than one agent; DPP, MLO configuration, traffic separation and backhaul configuration; fragmented inbound CMDUs. The optimizer only advises: automatic steering is off and it has no candidate measurements yet.

This is an experimental multi-agent lab, not a certified or complete EasyMesh controller. Its Profile 1/2 advertisement is a lab persona, not a claim of conformance.

Run it

Offline, without a device

The unit tests use synthetic identities and a synthetic M1; they send nothing and need no root. The panel starts with no live agent.

python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m unittest -v test_wsc test_controller test_protocol test_speed test_telemetry test_optimizer
.venv/bin/python panel_server.py        # http://127.0.0.1:8765

The lab VM

From a clean checkout on any Linux host with LXD VM support, a managed bridge and a storage pool. Nothing host-specific is assumed: the names and addresses are inputs.

python3 deploy/lxd-vm/build_vm.py \
  --name mesh-lab --host-ip HOST_LAN_IP --guest-ip UNUSED_VM_IP \
  --network MANAGEMENT_BRIDGE --pool STORAGE_POOL \
  --lab-mac ADAPTER_MAC --target AGENT_AL_MAC \
  --allow-client BROWSER_IP

The build never attaches hardware: the USB Ethernet adapter (by vendor, product and serial) and the enrolled Wi-Fi clients are handed over explicitly, and onboarding starts paused. The deployment guide covers the handover, the endpoints, validation and rollback.
